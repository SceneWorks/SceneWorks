# S9 normal-product physical guardian

This source implements the physical adapter required by `h3-veda-acceptance.mjs`. It has not launched a native product server, worker or GPU during development. CPU tests use fake product/process/queue interfaces and actual explicitly synthetic CPU subprocesses/HTTP service with a temporary CPU-only flock. They never claim either canonical GPU/nax lock. The coordinator registers `scripts/h3-veda-guardian.test.mjs` in the existing explicit package test list during integration; this isolated branch intentionally leaves `package.json` untouched.

## Exact binding and normal process ownership

`physicalGuardAdapter` points to the byte-bound `scripts/h3-veda-guard-adapter.mjs`; its hash and the Python guardian hash occur in `sourceFreeze.files`. Runner `guardian` additionally binds `{pythonPath,guardianSource:{path,bytes,sha256},maxSeconds,cleanupSeconds,dataDir,configDir,port}`. Python must be >=3.10 for the unchanged inference policy. maxSeconds is1–3600 and cleanupSeconds1–60. The isolated normal API URL must be `http://127.0.0.1:<port>`; dataDir/configDir are inside the external run directory, never installed/private product workspaces. The data directory contains an explicit prepared `s9-workspace-owner.json` equal to `{campaignId,sourceFreezeSha256:sha256(canonical(sourceFreeze)),projectId}`. Config staging must contain the exact byte-identical source catalog manifests. Startup refuses stale/dirty source, wrong binaries, foreign workspace, unbound source or occupied listener. Guardian/API authentication secrets are not written into evidence; `SCENEWORKS_TOKEN` is required at runtime. A private0600 control file carries the task IPC token, not an API secret.

The adapter launches a detached task-scoped guardian and authenticates live local IPC with its random owner token and complete manifest fingerprint. It resumes only that exact live owner, or a verified closed receipt with services drained, token hash/pid/fingerprint identity and prior owner exit. A refused/dead IPC response never proves absence of an old physical owner. The guardian directly starts the source-attested ordinary API binary and same worker-entry binary with `SCENEWORKS_WORKER_ONLY=1`, isolated `SCENEWORKS_DATA_DIR`/jobsDB/config/port, `SCENEWORKS_API_URL`, access token and `SCENEWORKS_PARENT_PID=<guardianPID>`. CPU utility routing stays CPU. It never invokes a native test/example generator. Worker selectors are explicit mlx or the selected physical CUDA index, never auto. CUDA_VISIBLE_DEVICES is the exact locked UUID (engine ordinal0); NVIDIA_VISIBLE_DEVICES preserves its source-proven physical index for normal worker discovery.

Mac ownership uses the two existing canonical flock files `/Users/michael/Documents/Codex/2026-10-10/epic-25140/s0-gpu-driver.lock` and `s2s4-aggregate-target.lock`, with descriptor device/inode verification. Root-owned API/worker processes inherit the actual lock descriptors, so guardian death does not release flock until inherited owners exit; the normal product's parent watchdog points at the guardian. Normal cleanup drains only the owned process groups and verifies no same-group descendants remain before closing locks. Windows uses `%PUBLIC%\SceneWorks\gpu-locks\<exact UUID>.lock` byte0 with msvcrt exclusive locking, plus the unchanged frozen inference WindowsJob implementation. Normal API/worker roots start suspended, are assigned to non-breakaway KILL_ON_JOB_CLOSE jobs and then resumed; assignment failure kills/reaps only that suspended owned child. Cleanup terminates/reaps the entire owned job before lock close. An incompatible enclosing Windows CI job is a refusal.

## Durable submission and controller loss

Before enqueue the JS driver atomically persists `submitting`, key, full request digest and request. It invokes the guardian's `submit` method. The guardian validates current physical ownership, fresh phase/queue admission, the source fingerprint and exactly one matching durable intent, fsyncs its own journal, starts/validates only the normal owned worker, and performs the ordinary **POST `/api/v1/video/jobs`** itself. It durably records the returned product job ID before responding over IPC. This covers controller SIGKILL during POST and response loss. A failed acknowledgement that provably never issued POST is recorded as `not_submitted`; a transport failure after POST remains ambiguous. Duplicate acknowledgement cannot erase an existing job or reenqueue it.

Controller PID/birth loss, retained uncertainty or maximum deadline causes the independent guardian to reconcile/cancel only guardian-acknowledged ordinary jobs, read back terminal status, drain/reap only its API/worker tree and recheck actual physical baseline before unlock. Foreign job IDs, project identities or marker mismatches are never canceled. Missing/duplicate/full history, unreachable API or incomplete descendant reaping cannot authorize unlock. Cleanup is bounded; if persisted queue uncertainty remains after services are drained, the guardian writes an explicit blocked receipt and retains its physical descriptors for owner reconciliation rather than fabricating safety. It performs no repeated render/reconciliation campaign in that blocked state. The blocked lock holder is a deliberate fail-closed state, not completed acceptance. Subsequent startup preserves old journal intents and will not start a GPU worker while an unresolved prior intent could replay.

Actual product/OS process crash behavior, especially Windows native handle semantics and Mac inherited-descriptor/watchdog exit, still requires the coordinator's pre-campaign operational proof under the exact permanent source/binary freeze. These CPU fakes do not constitute generated media, native hardware acceptance or Michael's quality decision. Per-step/host-device peak telemetry is independently owned and untouched here.

## Per-arm process lifetimes and completion receipts

Every admission stops the preceding terminal owned worker before the unchanged idle check. Dense and sparse arms use distinct fresh PID/birth lifetimes to avoid retained CUDA pureC contexts and cumulative MLX allocator peaks. The logical worker ID, binary, actual configuration, backend, physical device and frozen campaign remain equal; the comparator must not require the same OS process or guardian token across campaign batches. No global allocator counter is reset and no idle policy is relaxed.

The adapter forwards `beforePhase(phase, context={})` unchanged. `collect-completed-evidence` requires exact `{key,jobId}`; the guardian verifies a fresh ordinary job GET's completed status, project and complete acknowledged source marker. It verifies the live worker against the descriptor durably recorded before POST, reaps that owned root and descendants, persists the closure, then performs physical/queue admission. The phase returns `drainedWorker` containing `schemaVersion:1`, `key`, `jobId`, `pid`, `birth`, `workerId`, `workerBinarySha256`, `workerConfigSha256`, `workerConfigBinding`, `backend`, `physicalGpuId`, `campaignId`, `sourceFingerprint`, `guardianOwnerTokenSha256`, `sourceFreezeSha256`, `lifecycle:"fresh_per_arm_process_drained_before_next_admission"`, `reaped:true`, `descendantsDrained:true`, actual `exitCode` and the preceding `admissionReceipt` with the secret token omitted. Repeated exact collection after response loss reuses only that durable closure, with no current worker and a fresh physical check.

`sourceFingerprint` is SHA256 of the canonical complete manifest; `sourceFreezeSha256` is SHA256 of canonical `manifest.sourceFreeze`. Canonical JSON recursively sorts object keys, uses compact separators and UTF-8. `workerConfigSha256` hashes canonical `workerConfigBinding:{configFiles:[{path,sha256}],environment:{...}}`. File paths are sorted relative paths under the actual configDir; their original bytes are SHA256-hashed before launch and rechecked before collection; symlinks are refused. The environment includes constructed SCENEWORKS variables except the access token and process-specific parent PID, CUDA/NVIDIA selectors and the offline flags. The binding is a guardian attestation of actual launch inputs; it is not an invented existing sourceFreeze aggregate. Paired comparison verifies its digest and equality, and independently checks each owned closure/source/device/request identity.

`h3-veda-guardian-operations.py` starts the real guardian state machine, Services and Locks with explicitly injectable synthetic CPU physical/product adapters. Its five bounded operational cases exercise actual controller SIGKILL, response loss after an ordinary-shaped POST, controller death during POST, absent ambiguous intent retaining the CPU-only lock after real service drainage, and two completed CPU jobs with distinct actual worker roots and equal binary/configuration receipts. Duplicate acknowledgement never causes a second POST. These prove controller/process/journal ordering on the tested POSIX host; they do not prove native media, canonical resource acquisition or Windows Job behavior.
