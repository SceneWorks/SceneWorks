## Paired performance option

Set `performance: true` in the existing Krea suite options to run the separate PERF-1/2 comparison. A preflight verifies the sampler observer against independently reviewed baseline and candidate worker-source digests. The performance build temporarily wraps the shared provider progress callback in each attempt-owned checkout and restores the exact source bytes after compiling. The receipt records both the original and resulting source digests plus the binary digest. The functional witness builds without the sampler observer and remains a separate artifact.

For each backend and case, the job first queues one priming request per side to condition OS and kernel caches. It then measures six ordered pairs, alternating base-first and head-first. Each observation uses a fresh GPU worker process with an empty model cache. The case, verified weights, device, request, effective adapter scales, Euler schedule, seed, and geometry stay fixed. Hires.fix measures the same worker-compiled linked checkpoint plan on every run. The first import per app produces the stamp reused in subsequent fresh states for that app.

The observer starts each native sampler interval before the first Euler evaluation and ends it at the provider’s pre-decode event, with backend synchronization at both boundaries. Both Hires.fix intervals are visible before the worker hides the intermediate decode from public events. The report retains those intervals separately and divides their sum by the ten actual steps. End-to-end time is measured from the public submit request to the first terminal SSE update carrying the persisted final asset.

The memory domains are the MLX allocator high-water and worker lifetime physical footprint on macOS. On Windows they are the worker’s `PeakWorkingSet64` and the highest valid Windows `GPU Process Memory` Dedicated Usage sample. Both Windows builds use the same counter and cadence. The collection binds the worker’s PID and creation time to the adapter identified by the leased CUDA UUID, its Windows adapter LUID, and its node. Missing coverage, stale readings, or an identity mismatch make the comparison inconclusive. Whole-device samples remain diagnostics.

The project owner approved the Windows counter for these Krea runs after NVIDIA documented that its process memory reading is unavailable under WDDM. The same physical GPU previously returned valid readings for both arms of a SceneWorks proof. The Windows counter measures dedicated GPU memory charged to the worker. Exact physical residency remains unmeasured. The approval covers this Krea comparison and its allocation witness. [NVIDIA driver reference](https://docs.nvidia.com/deploy/nvml-api/latest/api/structnvmlProcessInfo__t.html) · [Earlier receipt from the same GPU](https://github.com/SceneWorks/inference/actions/runs/44901240422/artifacts/14709742656)

The scoring method is the six-pair procedure from inference `b2452ead6`. For both timing measures the report gives the median head/base ratio and its 96.875% min/max interval. An upper bound at or below 1.02 passes, a lower bound above 1.02 fails, and overlap is inconclusive. Each memory domain compares the highest valid observation from each side at the same 1.02 ceiling. The aggregate execution ceiling is 210 minutes. Missing pairs at that ceiling stay inconclusive and require a decision; the driver never extends the sample count or changes the ceiling after seeing the head.

## Production-shape Candle allocation witness

Set `allocation: true` in the Krea suite options with `backend=candle` and candidate inference SHA `5b7bd9690e084b8fe9ad746b74560cea601e973d`. SceneWorks pins the vendored Candle projection API at that same revision. Enable `download_missing` and set `preflight_only: false` for the render. The driver stages only the existing linked BF16 checkpoint and its companion files. It builds and runs the corrected candidate once. The frozen baseline remains a catalog check for this mode and runs at smaller geometries in the separate fidelity and timing profiles.

The candidate uses the original prompt and seed at 1120² base and 2240² refinement. The public request authors eight base and four refinement steps at denoising strength 0.5, so the worker emits ten executed ticks. The public file and library checks require one final 2240² PNG. The existing exact-device lease requires 75,776 MiB free device memory. The arm has five minutes for claim and thirty for execution, a 55-minute driver ceiling, and an 85-minute lease budget including admission wait.

The build-only observer binds to the exact candidate worker source. Only the owned GPU worker starts with the private 64 GiB CUDA proof pool. The driver reports cumulative USED and RESERVED high-water counters at the first step after conditioning, the pre-decode event, and successful provider return for each pass. The stream-ordered pool counters cover allocations in that pool through those boundaries. The report separately gives Windows sampled dedicated GPU memory for the exact worker and leased adapter, and the worker’s Windows lifetime working set. Missing or unavailable attribution leaves the witness inconclusive.

The source-priced 2240² reference encode requires 26,974,617,600 workspace bytes, including 17,340,825,600 bytes for im2col. The checked pinned files carry 35,666,639,636 bytes of weight payload plus headers. Using their full sizes as a conservative weight input gives about 58.36 GiB including RGB, latent, and prompt terms, with roughly 5.64 GiB left in the pool. The lease preserves at least 10 GiB outside the pool. These are projected reserves. The candidate must expose its runtime context and configure a scope for each geometry. The receipt compares its predicted additional device bytes with its available additional bytes, the pool’s absolute high-water marks with its pool cap, and the Windows working set with the worker containment limit. The sampled process device peak is preserved separately because its domain includes allocations outside the pool.
